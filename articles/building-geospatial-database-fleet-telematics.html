Building a Geospatial Database for Real-Time Fleet Tracking with PostgreSQL, PostGIS and Redis

Nov 23, 2026 · Erick Mulama Shituku · Geospatial Engineering

Introduction

Every day, transport companies rely on trucks to move goods between cities, across borders, and to their final destinations. Managing these movements requires knowing where vehicles are, whether they are following assigned routes, and whether deliveries are progressing as expected.

GPS trackers installed in vehicles regularly transmit location, speed, direction, and sometimes engine or fuel information. Collecting these messages is only the beginning. They must be received, stored, and processed before they can support live monitoring or useful decisions.

This raised a practical question as I developed FleetPulse: how can a database continuously receive vehicle tracking data while remaining responsive enough for live maps and geographic analysis?

What is FleetPulse?

FleetPulse is a fleet management and operations platform I am developing to help transport and logistics companies manage vehicles, drivers, trips, and day-to-day operations from one system.

The idea grew from my experience in fleet tracking and transport operations in East Africa, particularly on the Tanzania–Rwanda corridor. Monitoring truck movements, following up on delays, and coordinating with drivers showed me that knowing a truck’s location rarely tells the whole story.

A truck stopped near a border crossing might be waiting for customs clearance, taking a scheduled break, or dealing with a mechanical problem. Understanding the situation requires combining GPS information with trip records, driver communication, and operational context.

FleetPulse aims to connect these pieces. Beyond a map of moving vehicles, it is being built to support trip management, route monitoring, driver records, maintenance, reporting, and operational follow-up. To do that reliably, it needs a strong foundation for location data.

Why the database matters

Consider 100 vehicles each reporting once every ten seconds. With uninterrupted reporting, that would generate 600 updates per minute, 36,000 per hour, and 864,000 per day—over 25 million in 30 days. These are illustrative calculations, not measured FleetPulse traffic; actual reporting varies with device settings, activity, and network conditions.

Each update may include coordinates, a timestamp, speed, heading, and sensor readings. The platform must keep historical positions for journey review while also making the latest known positions available quickly to fleet managers.

Those are different workloads: one needs durable history; the other needs fast access to current information. Treating them as the same problem can create unnecessary database work.

Choosing PostgreSQL and PostGIS

PostgreSQL is the main relational database behind FleetPulse. It organizes vehicles, tracking devices, trips, and related operational records, allowing the application to connect location history with the business activities it represents.

PostGIS is an extension to PostgreSQL that adds geographic data types and spatial functions. Instead of storing longitude and latitude only as unrelated numbers, the database can represent a position as a geographic point and compare it with depots, geofences, and route corridors.

For example, PostGIS can help answer whether a truck is inside a depot, whether it has moved outside a designated corridor, or which recorded points belong to a particular journey. The choice of coordinate reference system and distance calculation method matters: longitude and latitude are angular coordinates, not distances in metres.

How GPS data enters the system

FleetPulse uses a Traccar protocol gateway to receive and decode messages from different GPS tracker types. The gateway forwards decoded positions to the application's telemetry ingestion layer, where the information can be handled in a consistent format.

This separation matters because the software that understands device-specific messages should not have to perform every database query or operational calculation itself. PostgreSQL and PostGIS preserve the location history; other components serve live updates and analyze the stream.

The architecture is designed around a flow from tracking device to protocol gateway, normalized telemetry ingestion, persistent storage, live state, background processing, and finally the dashboard.

Why Redis is part of the design

A fleet manager viewing a live map normally wants each vehicle's latest known location, not its entire history. Repeatedly searching a growing historical table for the newest point is work that can be avoided with a separate live-state mechanism.

FleetPulse uses Redis for live position state and Redis Streams for event processing. Redis provides fast access to frequently changing information, while PostgreSQL remains the durable record of historical and operational data.

Django Channels delivers live information to the dashboard over WebSockets, which allow the server to push updates without requiring the browser to request the entire map state again and again.

Redis is not a substitute for durable telemetry storage. Its role is to support the parts of the system that need rapid access to recent state or asynchronous event delivery.

Processing trips, stops, and other events

A single GPS point cannot tell us why a vehicle stopped. Understanding movement requires comparing positions across time and sometimes against geographic boundaries.

FleetPulse has dedicated processing components for trips, stops, parking, speeding, route deviations, and other operational events. Scheduled background workers perform this analysis separately from ordinary application requests.

This helps avoid making every incoming message wait for all downstream calculations to finish. It also means that receiving a position and completing the analysis associated with it are separate steps, which must be monitored independently.

Thinking about performance and reliability

Different questions require different database access patterns. Retrieving a vehicle's latest position, reconstructing months of movement, and checking whether a point lies inside a geofence are not the same kind of query.

PostgreSQL offers B-tree indexes for common identifier and time-based lookups, while PostGIS can use spatial indexes such as GiST for suitable geographic queries. Time-based partitioning can also be evaluated as historical tables grow. These are optimization options, not claims that every technique has already been deployed in FleetPulse.

More indexes are not automatically better: they consume storage and add work during inserts. Real optimization requires looking at actual queries, execution plans, ingestion rates, and response times.

Telemetry also arrives under imperfect conditions. Devices can lose connectivity and upload buffered messages later, so device timestamps may differ from server receipt times. Retries, duplicate records, and messages arriving out of order all need careful treatment.

FleetPulse is under active development, with physical tracker testing and production-scale validation still to be completed. I therefore treat low latency and reliability as design goals to test, not as performance results already proven.

What I learned

The most useful lesson has been that a responsive geospatial system is not built by asking one database to do everything. Durable history, current vehicle state, and computationally expensive event analysis have different needs.

PostgreSQL and PostGIS provide the foundation for storing and understanding vehicle movement. Redis helps make current information available quickly, while dedicated workers keep operational analysis separate from the incoming data path.

The next step is to measure the architecture under realistic device traffic: ingestion throughput, query latency, event-processing delay, and the time between receiving a position and displaying it on the map.

For me, this work brings together geospatial analysis and software engineering around a practical problem. A GPS coordinate becomes useful when a system can explain where a vehicle is, where it has been, and what its movement means for the operation.

Technologies: PostgreSQL, PostGIS, Redis, Redis Streams, Traccar, Django, Django Channels, Python, Docker and React. Project: FleetPulse.
